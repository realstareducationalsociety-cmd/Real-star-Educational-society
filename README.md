# Real Star Management System (RSMS) — نسخه آزمایشی 0.1

این پروژه آغاز عملی سیستم داخلی مدیریت **مجتمع آموزشی ریل استار** است. رابط کاربری به زبان دری و راست‌به‌چپ (RTL) می‌باشد. فیس و حساب‌ها به روپیه پاکستانی (`PKR`) ثبت می‌شوند.

> **مهم:** این نسخه، بنیاد عملی اولیه است، نه سیستم مالی نهایی آزمایش‌شده برای استفاده واقعی با پول و معلومات حساس. پیش از کاربرد رسمی، باید تست‌های دیتابیس، نسخه پشتیبان، سیاست‌های حسابداری و صلاحیت‌ها بررسی شوند.

## قابلیت‌های موجود در این نسخه

- ورود امن کارمندان از طریق Supabase Auth؛ نقش‌های `admin`، `accountant`، `registrar` با کنترل دسترسی دیتابیس (RLS).
- ثبت و اصلاح پروفایل شاگردان با نمبر دائمی، و ثبت استادان و صنف‌ها.
- اضافه‌کردن یک شاگرد به چند صنف، با یک پروفایل مشترک.
- ثبت ماهانهٔ تأییدشده برای شاگرد جدید یا قبلی؛ تمدید گروهی، تاریخچه و لغو بدون حذف سابقه.
- بازکردن ماه مالی بدون تمدید خودکار؛ فقط اشتراک‌های تأییدشده در شمارش و فیس ماه می‌آیند.
- شمارش اصلی شاگردان براساس اشتراک شاگرد-صنف-ماه، با نمایش جداگانهٔ پروفایل‌های یکتا.
- حفظ فیس اصلی صنف و فیس قابل محاسبه جداگانه؛ ثبت‌نام پس از روز بیستم با نصف فیس ماهانه محاسبه می‌شود.
- استحقاق استاد برابر ۵۰٪ فیس قابل محاسبه است؛ تخفیف عادی از سهم مرکز کم می‌شود.
- تنظیم دستی سهم استاد و اداره توسط مدیر با دلیل و سابقهٔ ممیزی؛ مجموع دو سهم باید برابر فیس قابل پرداخت باشد.
- تصفیه قسمی استاد به تفکیک **ماه، صنف، استاد**، همراه با سوابق.
- ثبت مصارف اداری و نمایش شاخص‌های داشبورد.
- امکان ابطال پرداخت فیس/تصفیه استاد با درج دلیل و نگهداری سابقه؛ بدون حذف مستقیم ثبت مالی.
- ساخت جداول اولیه شرکا، کتاب‌های امانی (متعلق به شخص دیگر) و چپترها برای توسعه آینده.

## پیش‌نیازها

- Node.js 22 یا جدیدتر و npm (نسخه سازگار با Nuxt 4)
- VS Code
- یک پروژه **جدید و جداگانه** در Supabase (ترجیحاً جدا از ویب‌سایت‌های قبلی)

## راه‌اندازی قدم‌به‌قدم

**۱.** پوشه پروژه را در VS Code باز کنید و در Terminal بنویسید:

```bash
npm install
```

**۲.** یک پروژه جدید در [Supabase](https://supabase.com/) بسازید. در SQL Editor، این migrationها را **به ترتیب** اجرا کنید:

```
supabase/migrations/001_initial.sql
supabase/migrations/002_chapters_books_printing.sql
supabase/migrations/003_confirmed_monthly_registration.sql
supabase/migrations/004_database_integrity.sql
supabase/migrations/005_historical_import_staging.sql
supabase/migrations/006_historical_operational_posting.sql
supabase/migrations/007_dashboard_registration.sql
supabase/migrations/008_registration_proration_and_settlements.sql
supabase/migrations/009_restore_dashboard_and_settlement_views.sql
```

`001` فقط برای دیتابیس خالی است. اگر `001` قبلاً اجرا شده، آن را دوباره اجرا نکنید؛ migrationهای بعدی را به ترتیب و فقط یک بار اجرا کنید. پیش از هر تغییر نسخهٔ پشتیبان بگیرید و اگر اجرای هر مرحله خطا داد، مرحله‌های بعد را اجرا نکنید تا خطا بررسی شود. Migrationهای `005` و `006` پس از migrationهای `001` تا `004` اجرا شوند؛ `007`، `008` و `009` نیز به کل زنجیره وابسته‌اند. Migration `008` فیس ثبت‌نام پس از روز بیستم را نصف فیس اصلی می‌سازد، فیس اصلی را جدا نگه می‌دارد، تاریخ و روش واقعی رسید ابتدایی را می‌خواهد و روش/ثبت‌کننده تصفیه استاد را نگهداری می‌کند. Migration `009` خلاصهٔ داشبورد را پس از proration بازسازی می‌کند تا `original_total` از فیس اصلی و payable/collection/balance از فیس قابل پرداخت و ledger واقعی خوانده شوند. فایل migration به‌تنهایی چیزی را به دیتابیس زنده منتقل نمی‌کند. وضعیت اتصال و چک‌لیست امن در [DATABASE_AUDIT.md](DATABASE_AUDIT.md) است. این فایل‌ها را در SQL Editor همان پروژه‌ای اجرا کنید که در `.env` تنظیم شده است.

### بازبینی واردات تاریخی

صفحهٔ مدیران `/imports` فایل بازبینی `.xlsx` را محلی می‌خواند و پس از تأیید مدیر، ردیف‌های دارای برگه/شمارهٔ منبع را در جداول staging ذخیره می‌کند. برای ردیف‌های پشتیبانی‌شده، مدیر باید نگاشت JSON را با هویت/ماه/مبلغ و تاریخ تأییدشده ذخیره کند؛ نام‌های مشابه هرگز خودکار ادغام نمی‌شوند. پیش‌نمایش، موارد آماده، موجودهای پیوندشده، تکراری‌ها، موارد نیازمند بازبینی و تراکنش‌های مالی نیازمند تأیید جداگانه را نشان می‌دهد. دکمهٔ **Post Approved Records to System** پس از تأیید صریح مدیر، هر نوبت حداکثر ۵۰۰ ردیف را در RPC تراکنشی دارای مجوز، قفل ماه مالی و کلیدهای idempotency منتقل می‌کند و پیش‌نمایش را تا پایان تازه می‌سازد. ردیف‌های نامطمئن یا بدون رسید تأییدشده همچنان در staging می‌مانند. ردیف‌های Books/Chapters برای فروش به قلم کاتالوگ عملیاتی موجود نیاز دارند؛ فروش فقط با تاریخ تأییدشده ثبت می‌شود و پرداخت جداگانه فقط با رسید تأییدشده منتقل می‌گردد. خلاصه‌ها و تصفیهٔ استاد به‌عنوان معاملهٔ واقعی ساخته نمی‌شوند. تصمیم‌های بازبینی دلیل ممیزی می‌خواهند و فایل تکراری با SHA-256 دوباره‌کاری نمی‌شود. فایل‌های حاوی نام، تماس و اطلاعات مالی را در `public/` قرار ندهید؛ کپی پروژهٔ فایل بازبینی باید در محل خصوصی بماند.

برای شمارش دقیق وضعیت دیتابیس هدف، فایل [`supabase/live_import_status.sql`](./supabase/live_import_status.sql) را در SQL Editor همان پروژه اجرا کنید؛ فقط یک جدول موقت در همان نشست می‌سازد و اطلاعات عملیاتی را تغییر نمی‌دهد. برای بررسی کامل schema و RLS از `supabase/audit_readonly.sql` استفاده کنید.

پیش از واردات تولیدی، مدیر دیتابیس باید پروژهٔ Supabase را با مقدار `.env` تطبیق دهد، از دیتابیس نسخهٔ پشتیبان بگیرد، وضعیت نصب و schema را بررسی کند و migrationهای موجود را به‌ترتیب روی دیتابیس آزمایشی اجرا کند. فقط پس از تأیید صریح برای تغییرات تولیدی، migrationهای مفقود را اعمال کرده و خروجی preview و SQL queryهای عملیاتی را بررسی کند. ردیف‌های `SummaryClasses`, `RegistrationLeads` و سایر خلاصه‌ها مرجع‌اند، نه تراکنش قابل ثبت؛ `PartnerNotes` فقط با تأیید مستقل transaction، partner، مبلغ و تاریخ قابل انتقال است. رکوردهای مالی بدون تاریخ/رسید قابل اتکا در ledger قطعی ثبت نمی‌شوند.

**۳.** از بخش **Authentication → Users** یک کاربر مدیر با ایمیل و رمز عبور قوی بسازید. `User UID` آن را کاپی کنید. در SQL Editor این دستور را با UID واقعی اجرا کنید:

```sql
insert into public.staff_profiles (id, full_name, role, is_active)
values ('USER_UUID_HERE', 'نام مدیر', 'admin', true);
```

بدون این قدم، ورود کاربر به پنل مجاز نمی‌شود. از ایمیل/رمز صرفاً برای حساب‌های کارمندی استفاده کنید و خودثبت‌نام آزاد را برای این پنل فعال نکنید.

**۴.** فایل `.env.example` را به `.env` کاپی کنید و `Project URL` و `anon/publishable key` از Supabase را وارد نمایید:

```bash
cp .env.example .env
```

در ویندوز می‌توانید فایل را دستی کاپی کنید یا این دستور PowerShell را اجرا نمایید:

```powershell
Copy-Item .env.example .env
```

**هرگز** `service_role`، `secret key` یا رمز دیتابیس را در متغیرهای `NUXT_PUBLIC_` نگذارید.

**۵.** ویب‌اپلیکیشن را اجرا کنید:

```bash
npm run dev
```

آدرس `http://localhost:3000` را باز کنید، با حساب مدیر وارد شوید.

## ترتیب درست کار روزمره

1. استادان را در صفحه **استادان** ثبت کنید.
2. صنف‌ها را در **صنف‌ها** ایجاد کنید، استاد و فیس اصلی را تعیین کنید.
3. شاگردان را در **شاگردان** ثبت نمایید.
4. از صفحه **ثبت‌نام در صنف‌ها** شاگردان را به صنف(های) مربوط اضافه کنید.
5. در صفحه **فیس و پرداخت‌ها** ماه مورد نظر را انتخاب و **ایجاد حساب ماه** را بزنید.
6. فیس ماه هر شاگرد را بررسی و تخفیف‌ها را مشخص کنید، سپس پرداخت‌ها را ثبت کنید.
7. از صفحه **تصفیه استادان** حساب مستقل هر صنف را ببینید و تصفیه‌ها را ثبت کنید.
8. مصارف عمومی را در **مصارف مجتمع** وارد کنید.

## قواعد مالی مهم

فرض کنیم فیس اصلی `2,000 Rs.` و تخفیف `500 Rs.` است:

| عنوان | مبلغ |
|---|---:|
| فیس اصلی | 2,000 |
| فیس قابل دریافت | 1,500 |
| استحقاق استاد (۵۰٪ فیس قابل محاسبه) | 1,000 |
| سهم مرکز پس از تخفیف | 500 |

اگر استاد پذیرفته باشد که ۲۰۰ روپیه از تخفیف را خودش متقبل شود، `teacher_discount_share = 200` و استحقاق استاد ۸۰۰ روپیه می‌شود؛ سهم مرکز در این مثال ۷۰۰ روپیه خواهد بود.

**پول دریافت‌شده از شاگرد** و **استحقاق استاد** دو عدد مستقل هستند؛ **مبلغ تصفیه‌شده با استاد** نیز جدا ثبت می‌شود. هنوز تصمیم نهایی مدیر درباره پرداخت استحقاق استاد از فیس‌های وصول‌نشده لازم است؛ نرم‌افزار به طور خودکار این دو را یکی نمی‌گیرد.

## تفکیک حساب‌های ویژه

- **سه شریک:** داده‌ها به صورت `partners` و `partner_transactions` تعریف شده‌اند. هر سه شریک باید `ownership_units=1` داشته باشند تا مالکیت مساوی (۱/۳) باشد. تقسیم خودکار مفاد پس از مصارف هنوز پیاده نشده است.
- **کتاب‌های امانی:** `books`, `book_sales`, `book_owner_settlements` مستقل هستند؛ تمام پول فروش کتاب مربوط مالک بیرونی است و هیچ مقدار آن عاید مجتمع نیست، و مبلغ متعلق به مالک باید تصفیه شود.
- **چپترها:** `chapters`, `chapter_sales` مستقل هستند؛ چاپ، فروش و مفاد چپتر نباید با پول کتاب‌ها یا فیس‌ها مخلوط شود.

## محدودیت‌های فعلی و کارهای مرحله بعد

1. صفحات مدیریتی شرکا، کتاب‌های امانی، چپترها، راپور مفاد خالص و تقسیم مفاد.
2. حاضری شاگردان، امتحانات، نتایج، کارت شاگردی و آرشیف اسناد.
3. عملیات اصلاح/ابطال مصارف، گزارش حسابرسی کامل، بستن و بازبینی ماه، گزارش اکسل/PDF.
4. واردکردن معلومات سپتمبر/اکتوبر/دسامبر فقط **بعد از تصفیه ثبت‌های تکراری و مشکلات تاریخ/فورمول**.
5. تست خودکار دیتابیس، تست امنیت نقش‌ها، تست تراکنش‌های هم‌زمان، مدیریت نسخه پشتیبان و بازیابی قبل از استفاده عملی.
6. چاپ رسید با لوگوی اصلی ریل استار (در این مرحله فایل لوگوی رسمی داخل پروژه گنجانده نشده است).

## معلومات شخصی و امنیت

- در نسخه اولیه از معلومات واقعی شاگردان به عنوان دیتای نمونه استفاده نشده است.
- همه جدول‌های خصوصی RLS دارند؛ کنترل دسترسی صرفاً وابسته به پنهان‌کردن دکمه‌ها نیست.
